# План на победу: Qazaq Loc QA (Grand Mobile × Decentrathon 6.0)

## 1. Как нас оценивают и что из этого следует

| Критерий | Вес | Как меряют | Вывод для нас |
|---|---|---|---|
| Детекция подложенных ошибок | 35% | Recall по ~100 подложенным с учётом **типа** + precision на 100 **случайных** находках | Тип ставим точно. Шум в report.json бьёт по precision напрямую. Реальные «органические» ошибки precision не портят, это честные находки |
| Качество исправлений | 35% | Слепое сравнение носителями 150 случайных **изменённых** строк: новая версия против старой | Каждая правка участвует в лотерее. Сомнительную строку не трогаем. Меняем только одобренное носителем |
| Универсальность | 15% | Работает на любом ARB, есть документация и тесты | Никакого хардкода под Grand Mobile в ядре, языковые профили конфигом, pytest на синтетике |
| Объяснимость | 15% | Понятные evidence и severity, мало шума | Evidence формулируем как факт с цифрами («12 символов против 4; ключ `*Button`; uz-вариант 5 символов») |

Главный принцип: **высокая точность важнее широты охвата**. Всё, в чём уверены слабо, идёт в отдельный файл
`hints.json` или в HTML под фильтром low. В report.json попадает только то, за что не стыдно перед жюри.

## 2. Что уже нашли при разведке данных (быстрые победы)

Без LLM, только правилами, уже видно около 80 из ~100 подложенных ошибок:

| Тип | Сколько видно | Как ловится |
|---|---|---|
| placeholder_mismatch | 12 | `{time}` → `time`, `{platformColo}`, `{leve}`, пропавший `{points}` |
| wrong_language | ~14 | Узбекская латиница (`Avtorizatsiya xatosi`, `Jami to‘lov:`), португальский (`launcherSettingsDeleteAccountConfirm`), английский (`Equipped`); совпадение kk с uz/en при отличии от ru |
| length_overflow | ~14 | Шаблонные хвосты к коротким строкам: «…режимін қосу және жалғастыру», «…бөліміне өту үшін басыңыз», «…туралы толық ақпарат алу үшін» |
| orthography | ~15 | Слово встречается 1 раз и без казахских букв, а вариант с ними частый: `жане/және`, `сыйлык`, `кайта`, `тандау`, `сагат`, `казына`, `жарыска`; латинская `i` в кириллице (`бөлімiне`, `өтiп`); латинская `c` (`көтерілеcің`) |
| suffix_harmony | 10 | `{provider}-ға`, `{price}-ге`, `{fromUser}-дан`, `{id}-ға`, `{bet}-ға GC` |
| untranslated | 16 | 12 ключей отсутствуют, 4 пустые строки |
| same_as_source | ~10–20 из 287 | Целые русские предложения (`bankConfirmHouse`, `birthday_info_more_play`, `footballTutorDesc31`, `laUnknownNetworkError`, `chaosStep3Part1Text`, `schTutorialT8S0`) против легитимных заимствований (`Профиль`, `Капот`) |

Остальные ~20 подложенных, скорее всего, это `machine_translation_suspect`, `glossary_violation`,
`inconsistent_term` и смысловые подмены. Подозрительные примеры: `marriage` Брак → «Заңға бағынушылық»,
`balance` → «қолма-қол ақша», `favorite` → «Қолжетерлік іс-әрекеттер», `rm_title_10` Имущество → «Таңдамалыларды
баптау», `tune_buy_headlights_color` → «Бағдаршамның түсі» (это «светофор»), `alabugaSchoolAllDay` круглосуточно →
«10.00-ден 22.00-ге дейін». Их ловит LLM-слой (см. ниже).

Структурные проблемы, которые тоже нужно отразить: 109 дублей ключей (10 с разными значениями), 2 лишних ключа.

## 3. Архитектура

```
locqa/
  arb.py          # парсер ARB: порядок, @@comment-разделы, дубли, @meta, номер строки
  icu.py          # токенизатор ICU (placeholder, plural/select, теги <g>), валидатор
  profiles/       # языковые профили: kk.yaml, uz.yaml (алфавит, «чужие» буквы, аффиксы, гармония)
  checks/         # по одному модулю на issue_type, общий интерфейс Check.run(ctx) -> [Finding]
  llm/            # LLM-судья: батчи по разделам, кэш на диске, подсчёт токенов и стоимости
  glossary.py     # загрузка CSV, сопоставление словоформ (стемминг по аффиксам kk)
  report/         # report.json, HTML (один файл, Jinja2), hints.json
  fix/            # генерация suggestion, сборка intl_kk_fixed.arb из решений ревьюера
  cli.py          # locqa check | locqa review | locqa apply | locqa translit
tests/            # pytest на синтетических ARB + инжектор ошибок
review_ui/        # мини-интерфейс для носителя
```

Стек: Python 3.11, Typer (CLI), Jinja2 (HTML), pytest. LLM через Claude API (Sonnet 5.5 для массовой проверки,
Opus 5.5 для генерации исправлений на спорных строках), кэш ответов по хэшу промпта.

### 3.1 Детекторы: правила (детерминированные, дают высокую точность)

1. **untranslated**: ключ отсутствует, значение пустое или из одних пробелов.
2. **placeholder_mismatch**: мультимножество плейсхолдеров `{x}`, `%s`, `<g>` в ru и цели. В evidence указать,
   какой именно пропал. Если похожий токен есть без скобок, suggestion восстанавливает скобки.
3. **plural_mismatch**: парсинг ICU `{n, plural, ...}`; нет `other`, формы не совпадают с CLDR для локали, сломаны скобки.
4. **same_as_source**: совпадение с ru минус allowlist. Allowlist строим автоматически: цифры и символы, бренды
   и латиница, одно слово, которое так же записано в uz/en транслитерацией (признак заимствования), имена
   (`*Name`, `*Mentor*`). Severity high для предложений (≥3 слов), low для одиночных слов.
5. **wrong_language**: доля латиницы для кириллической цели; узбекские маркеры (`o‘ g‘ ʼ -ni -lar -ga`, `sh ch`);
   точное совпадение с uz/en при отличии от ru; идентификатор языка (fastText lid.176 или символьные n-граммы),
   обученный на самих ru/uz/en/kk файлах.
6. **orthography**: (а) смешение письменностей внутри слова; (б) нормализация `ә→а, қ→к, ң→н…`: редкое слово без
   казахских букв при частом варианте с ними; (в) словарь kk (Hunspell kk или частотник из открытого корпуса)
   для явных опечаток. Важно: `бас`/`бәс`, `болу`/`бөлу` — это разные слова, поэтому учитывать контекст и порог частоты.
7. **suffix_harmony**: регэксп `({x}|%s)-?[аффикс]` по списку казахских падежных и притяжательных окончаний
   из профиля. Suggestion: переформулировка (см. бонус 4) или пометка «требует обработки в коде».
8. **length_overflow**: ключ похож на UI-элемент (`button|btn|tab|title|header|label`, короткий ru ≤ 20,
   CAPS, раздел), и `len(kk)/len(ru)` выше порога, откалиброванного по распределению всего файла. Дополнительный
   сигнал: uz и en в той же строке короткие. Отдельно считаем самую длинную строку после `\n`.
9. **glossary_violation / inconsistent_term**: по глоссарию ищем ru-термин в источнике (со словоформами), затем
   проверяем, что в цели стоит kk-термин (со стеммингом аффиксов). Inconsistent: для каждого ru-термина собираем
   распределение переводов по всем ключам; редкий вариант при доминирующем помечаем, в evidence приводим счётчик
   («`Grand Coins` 11 раз, `GC` 11 раз, `Grand Coin` 2 раза»).

### 3.2 Детектор: LLM-судья (machine_translation_suspect и смысл)

- Подаём батч из 30–50 строк одного `@@comment`-раздела: ru + en + uz + kk + имя ключа + соседние строки.
  en и uz служат вторым источником смысла.
- Ответ строго в JSON-схеме: `issue_type`, evidence на русском, suggestion, confidence. Temperature 0.
- Флагаем только при confidence ≥ порога и при согласии двух прогонов (self-consistency) или двух моделей.
- Нашли смысловую подмену (`Брак → Заңға бағынушылық`): тип `machine_translation_suspect`.
- Стоимость: ~5 500 строк × ~150 токенов ≈ 0,8–1 M входных токенов на прогон. Точные цифры считаем по
  фактическим usage из ответов и пишем в отчёт.

### 3.3 Как честно измерить качество (у нас нет ключа ответов)

1. **Инжектор синтетических ошибок** (`tests/inject.py`): берём kk, вставляем N ошибок каждого типа по тем же
   рецептам, что видим в данных (убрать скобки у плейсхолдера, заменить қ→к, дописать хвост, подставить uz-строку,
   подставить ru-предложение, жёсткий аффикс). Считаем recall по типам. Это сразу и тесты, и метрика для отчёта.
2. **Ручная разметка precision**: носитель размечает 100 случайных находок из нашего report.json, так же как жюри.
   Цель: precision ≥ 0,9. Результат публикуем в методологии.
3. Пороги каждого детектора подбираем по этим двум метрикам.

## 4. Исправления и работа носителя (35% оценки)

Поток: `locqa check` → кандидаты с suggestion → **review UI** → решения `accept / edit / reject` → `locqa apply`.

- Review UI: одна HTML-страница или Streamlit. Показываем ru / en / uz / текущий kk / предложение / evidence,
  горячие клавиши (Enter = принять, E = править, R = отклонить). Решения пишутся в `decisions.jsonl`
  (кто проверил, когда, исходная и итоговая строка).
- Приоритет очереди: сначала high-severity детерминированные (быстрые, 2–3 секунды на строку), потом LLM-находки,
  потом «улучшения» вроде машинных калек.
- Реалистичная пропускная способность: 1 носитель ≈ 150–250 строк в час на простых правках. Цель 400–600
  проверенных строк. Всё, что носитель отклонил или не успел, **не меняем**.
- Флаг проверки в ARB. Нужно проверить, что `flutter gen-l10n` его пропускает:
  ```json
  "bankTotalToPay": "Төлеуге барлығы:",
  "@bankTotalToPay": { "x-locqa": { "reviewed_by_human": true, "reviewer": "A.", "original": "Jami to‘lov:", "issues": ["wrong_language"] } }
  ```
  Запасной вариант, если gen-l10n ругается: флаг внутри `description` и дублирующий `intl_kk_fixed.review.csv`.
- Дубли ключей в fixed-файле схлопываем до одного (действующего) значения. 12 отсутствующих ключей переводим
  и тоже проверяем носителем.
- Финальная проверка: собрать минимальный Flutter-проект с `l10n.yaml` (template = ru) и прогнать `flutter gen-l10n`
  на `intl_kk_fixed.arb`. Шаг включаем в CI.

## 5. Глоссарий (`glossary.csv`)

Колонки: `ru, kk, en, uz, part_of_speech, forbidden_variants, slang, note`.
- Ядро из ТЗ: фракция, семья (отбасы), Grand Coins (GC/ГК), бизнес, варн, мут, фура.
- Расширяем автоматически: частотные ru n-граммы из имён разделов и UI-строк, выравнивание ru↔kk по всем ключам
  (какой kk-перевод доминирует), затем носитель утверждает. Цель 80–150 терминов.
- Сленг указываем явно: «варн» не переводим как «ескерту», если игроки так не говорят. Решение принимает носитель,
  и оно записывается в note.

## 6. Бонусы (по ценности для жюри)

1. **Узбекский** (почти бесплатно при профилях): `locqa check --target intl_uz.arb --profile uz`. Ищем кириллицу
   и русский текст в латинском uz, плейсхолдеры, апострофы `‘ ʼ '` (смесь вариантов — orthography).
   Уже видны 3 placeholder_mismatch.
2. **Транслитерация kk в латиницу** по официальному алфавиту 2021 года: `locqa translit` + проверка длины против ru.
   Таблицу соответствий сверить с официальным указом перед реализацией.
3. **GitHub Action**: на PR с изменением `*.arb` запускается `locqa check`, падает на high, комментирует PR
   сводкой. 30 минут работы, хорошо смотрится в демо.
4. **Переформулировка для аффиксов**: шаблоны вида `{price}-ге сатып алу` → `Сатып алу: {price}`,
   `{fromUser}-дан {toUser}-ға қарсы` → `Шағым: {fromUser} → {toUser}`; LLM предлагает, носитель подтверждает.
   Плюс режим «code-handled»: пример Dart-функции выбора аффикса по последней гласной для разработчиков.

## 10. Риски

| Риск | Что делаем |
|---|---|
| gen-l10n не принимает `x-` метаданные или ключи вроде `inventoryEquipped@description` | Проверить в первые 2 часа, держать запасной формат флага |
| Не хватает времени носителя | Сортировать очередь по ценности, правки делать только по проверенному; лучше 300 отличных правок, чем 1000 средних |
| LLM шумит, precision падает | Порог по confidence + self-consistency; низкоуверенные находки только в hints.json |
| Неверный issue_type для находки с несколькими проблемами | На одну строку можно выдать несколько находок разных типов (например, placeholder + suffix) |
| Утечка данных в публичный репозиторий | `.gitignore` с первого коммита, фикстуры только синтетические |
