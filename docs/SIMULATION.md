# Прогон LLM-конвейера на имитации модели

Цель: проверить весь поток (правила → LLM-проверка → исправления → валидация) до того, как тратить деньги и время
носителя. Найти провалы, недостающие инструменты и решить, как делить конвейер на части.

## Как устроена имитация

- `locqa/judge.py` собирает батчи и промпты точно так же, как в боевом режиме, но `FileBackend` вместо отправки в
  OpenRouter пишет запросы в `out/sim/<cycle>/requests/`.
- Роль модели играли агенты на Claude Sonnet. Каждый видел **только** файл запроса (system + user) и отвечал так, как
  ответила бы `anthropic/claude-sonnet-5.5` (проверка) или `claude-opus-5.5` (исправления).
- Ответы разбирались боевым парсером с валидацией схемы, затем `tools/sim/sim.py evaluate` и `tools/sim/sim_fix.py evaluate`.
- Выборка: 9 разделов игры, **588 строк** (DOCS, DONATE, TUNING, FUEL, BANK, FAMILY, BONES, JUNGLE_TREASURES, ALABUGA_SHCOOL).
- Разметка:
  - **9 подложенных нами ошибок** с известным ответом (глоссарий «ЖАНҰЯ», «Топ» вместо фракции, отрицание вместо
    утверждения, 13:00 → 15:00, русский порядок слов, перепутанные КАПОТ и ШАТЫР, «сұйық жетек» вместо гидравлики,
    калька «Қабылдау қатысуды»);
  - **22 подозрительные органические строки**, отобранные вручную (`Брак → «Законопослушность»`, `КРУПЬЕ → «крупная вещь»`…);
  - находки правил в этой выборке (15 ключей).

Ограничения имитации: модель-имитатор из того же семейства, что и боевая, но это не она; precision ниже — моя ручная
оценка, а не оценка носителя.

## Каких инструментов не хватило

Сделано по ходу прогона (`locqa/checks/hints.py`):
- `copied_translation` — kk совпадает с переводом другого ключа при разных ru и en (`Брак` = `Законопослушность`,
  `В баке` = `Текущий уровень`). Сам по себе шумный (238 подсказок), поэтому это только сигнал для LLM.
- `number_mismatch` — числа в ru и kk расходятся (`«от 1 до 70»` → `«3-тен 90»`, пропало «50» в `hud_play_50_hours`).
- `fragment` — куски фраз, склеиваемых в коде, вместе с соседними ключами (109 подсказок).
- `same_single_word` — однословное совпадение с ru; решает LLM: заимствование или забыли перевести.
- Валидатор исправлений `locqa/fix.py`: плейсхолдеры, ICU, `\n`, латиница, длина, аффикс после плейсхолдера, запреты глоссария.

Сделано после прогона:
1. **Сквозной словарь терминов** (`rules.term_groups`, подсказка `term_variants`): одна и та же короткая ru-строка
   и все её kk-варианты по файлу. 85 групп с разнобоем. **Урок: большинство само бывает неверным** — «Отмена» →
   «БАСТАУ» в 5 ключах против правильного «Болдырмау» в 2, «Выбрать» → «Аймақты таңдаңыз» ×3, «Баланс» →
   «қолма-қол ақша» ×3. Поэтому автоматическая находка «меньшинство не совпало с большинством» отключена: она помечала
   бы правильные строки и предлагала неверную замену. Группы решает голосование (`decide.vote_questions`) или LLM.

Ещё не сделано, нужно:
1. **Слияние находок** правил и LLM по ключу: одна строка может получить `length_overflow` от правил и
   `machine_translation_suspect` от LLM (как `marriage`, `favorite`). Оставляем обе находки (обе правдивы), а в
   ревью показываем одной карточкой.
2. **Учёт фрагментов в правилах**: пустое значение у `*Prefix` не всегда ошибка.
3. **Очередь ревью по ценности**: сначала high-находки с проверенным исправлением, потом спорные; поле `confidence`
   из fix v2 даёт сортировку.

## Делить ли конвейер на части — да

Монолитный промпт (c1) находит много, но путает типы и шумит. Разделение дало то же качество поиска при точности
~85–90% и нулевом шуме. Итоговая схема:

```
1. Правила (rules.py)           детерминированные типы, с suggestion там, где правка механическая
2. Подсказки (hints.py)         слабые сигналы → только как контекст для LLM
3. LLM-проверка (judge v3)      только смысл/термины, батчи по разделу ≤ 40 строк, already_found + tool_hints
4. Слияние                      правила ∪ LLM по ключу; source_notes → отдельный файл для студии
5. LLM-исправления (fix v2)     только для находок без suggestion; fragment_context; needs_code / needs_context
6. Валидатор (fix.py)           не прошло → не показываем носителю
7. Ревью носителя               только одобренное попадает в intl_kk_fixed.arb
8. apply + flutter gen-l10n
```

Дробить проверку на отдельные промпты по типам не нужно: v2/v3 уже точны. Следующее разумное разделение —
отдельный **глобальный проход согласованности** на основе словаря терминов, а не ещё один батчевый промпт.

## Что осталось улучшить в промптах (v4)

По фидбэку агентов c4:
- **Переносы `\n`**: правило «сохраняй `\n`» противоречит случаям, где в ru перенос есть, а в kk нет. Уточнить:
  берём раскладку строк текущего kk, если она не сломана.
- **Строка с двумя смысловыми ошибками** — одна находка или две? Решить: одна находка, обе ошибки в evidence.
- **Неизвестный термин**: «минимальная правка» противоречит «null, если не уверен». Уточнить: ошибку сообщаем
  всегда, `suggestion: null` допустим.
- `same_as_source` и в списке типов LLM, и среди «проверено автоматически». Переформулировать: только для
  `same_single_word`.

## Как повторить

```bash
python tools/sim/sim.py prepare c6 v3 --with-rules --glossary out/sim/glossary_core.csv
# ...ответы в out/sim/c6/responses/<batch>.txt (имитатор или реальная модель)...
python tools/sim/sim.py evaluate c6          # eval.json, extra.md, dropped.md, source_notes.md
python tools/sim/sim_fix.py prepare c7 --prompt v2 && python tools/sim/sim_fix.py evaluate c7   # fixes.md
```

Исправления, реальный `claude-opus-5.5` (r5): 63/66 прошли валидатор, 3 «нужен контекст», 1 отклонён (фрагмент
длиннее лимита кнопки). $0,39.

Новые провалы, которых не было в имитации:
- в `suggestion` модель кладёт комментарии и варианты («сатып алушы (жинаушы)») → `judge._commentary` обнуляет такое
  предложение;
- модель нарушает порог «ниже 0.7 не сообщай» (находка с 0.3) → её отсекает `--min-confidence` и отправляет в QA.

Выводы:
- Грубые смысловые ошибки («Брак» → «законопослушность», «КРУПЬЕ» → «крупная вещь», «Отмена» → «НАЧАТЬ») ловят все.
- Тонкую казахскую лексику маленькие модели не знают: «Бастаушыға» (вместо «лаунчер») ни одна уверенно не поймала,

- Нарушение глоссария «ЖАНҰЯ» пропустили все пять (0.03–0.19): глоссария в state нет, а сами они его не знают.
- Как основной искатель decision-модели проигрывают Sonnet. Их место: `drex-max` — фильтр «предпочтёт ли носитель
  исправление» перед ревью; `d1-ultra` — дешёвая страховочная сеть (p ≥ 0.9 там, где правила и LLM промолчали →
  очередь QA). Смешивать их вероятность с confidence Sonnet нельзя: настоящие глоссарийные находки утонут в QA.
